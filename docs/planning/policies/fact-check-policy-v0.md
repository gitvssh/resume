# Fact-Check Policy v0

- 상태: `draft`
- 마지막 수정일: `2026-04-10`
- 작성자: `lsh`

## 1. 목적

이 문서는 `Resume Tailor` v0에서 맞춤 이력서 재작성 결과가 사실을 벗어나지 않도록 통제하는 최소 정책이다.

이 정책의 목표:

- 없는 경험 생성 방지
- 없는 수치 생성 방지
- 역할 부풀리기 방지
- JD에 맞춘 표현 강화와 허위 생성의 경계 고정

이 정책은 [Backend Resume Rubric v0](../rubrics/backend-rubric-v0.md)의 `Gate A. 사실 보존`을 구현 수준으로 내린 것이다.

## 2. 핵심 원칙

- 원문에 없는 사실은 추가하지 않는다.
- 원문에 없는 수치나 비율은 생성하지 않는다.
- 원문보다 더 큰 책임이나 의사결정 권한을 단정하지 않는다.
- JD에 맞춘 강조는 허용하지만, JD에 맞춘 사실 생성은 금지한다.
- 검증이 어려운 문장은 사용자 확인 없이는 확정 문장으로 출력하지 않는다.

## 3. 허용 / 금지 범위

### 허용

- 같은 사실을 더 명확하고 간결하게 다시 쓰기
- 같은 사실을 JD 목적에 맞게 앞쪽으로 재배치하기
- 모호한 문장을 구조적으로 정리하기
- 원문에 이미 있는 수치를 더 잘 드러내도록 배치하기
- 이미 있는 경험을 더 적절한 키워드로 표현하기

### 금지

- 원문에 없는 회사/프로젝트/기술 경험 추가
- 원문에 없는 수치, 퍼센트, 트래픽 규모, 비용절감 수치 추가
- `주도`, `설계`, `리드`, `오너십`처럼 역할 강도를 높여 단정하는 표현 추가
- JD 요구사항을 맞추기 위해 없는 경험을 암시하는 표현 추가
- 사실 확인이 안 된 해석을 결과로 단정

## 4. 위험 문장 유형

아래 문장은 우선 검토 대상으로 본다.

### Type A. 수치 생성 위험

예:

- `성능을 30% 개선`
- `월간 100만 사용자 트래픽 처리`
- `비용을 20% 절감`

판정 원칙:

- 원문에 수치 근거가 없으면 자동 생성 금지

### Type B. 역할 강화 위험

예:

- `전체 시스템 아키텍처를 리드`
- `핵심 의사결정을 주도`
- `대규모 분산 시스템을 설계`

판정 원칙:

- 원문에 `주도`, `설계`, `리딩`, `오너십` 근거가 없으면 보수적으로 낮춘다.

### Type C. JD 유도 허위 위험

예:

- JD에 Kafka가 있으니 원문에 없는 Kafka 경험을 암시
- JD에 대용량 처리 경험이 있으니 원문에 없는 scale 경험을 일반화

판정 원칙:

- JD는 강조 순서를 바꾸는 근거일 뿐, 새 경험을 만드는 근거가 아니다.

### Type D. 과도한 일반화 위험

예:

- 작은 프로젝트 경험을 `대규모 서비스 운영 경험`으로 확대
- 일부 참여를 `end-to-end ownership`으로 확대

판정 원칙:

- 규모, 범위, 책임은 보수적으로 유지한다.

## 5. 판정 단계

v0에서는 아래 4단계로 fact-check를 수행한다.

### Step 1. 원문 근거 연결

재작성된 각 핵심 bullet 또는 문장에 대해 아래를 연결한다.

- 어떤 `experience` 또는 `project`에서 왔는가
- 어떤 `achievement` 또는 `source_blocks`를 근거로 삼았는가
- 어떤 JD requirement를 반영했는가

이 단계에서 근거가 비어 있으면 `Gate A` 후보 실패로 본다.

### Step 2. 위험 패턴 탐지

아래 패턴이 새로 들어갔는지 검사한다.

- 새로운 숫자
- 새로운 규모 표현
- 새로운 기술명
- 역할 강도 상승 표현
- JD 키워드의 직접 삽입

권장 방식:

- 규칙 기반 탐지 우선
- 필요한 경우 LLM 2차 검토

### Step 3. 보수적 재서술 확인

위험 패턴이 잡히면 아래 중 하나로 처리한다.

- 원문 수준으로 낮춘다
- 더 보수적인 표현으로 바꾼다
- 사용자 확인 필요 상태로 표기한다
- 근거가 없으면 제거한다

### Step 4. 최종 게이트 판정

아래 중 하나라도 충족하면 `Gate A = fail`

- 근거 없는 새 사실 존재
- 근거 없는 새 수치 존재
- 근거 없는 역할 강화 존재

모두 통과하면 `Gate A = pass`

## 6. 우선 적용 규칙

v0에서 우선 적용할 규칙은 아래 6개다.

1. 원문에 없는 숫자는 쓰지 않는다.
2. 원문에 없는 기술 스택은 쓰지 않는다.
3. 원문에 없는 `설계`, `주도`, `리딩`, `오너십` 표현은 쓰지 않는다.
4. JD 키워드는 원문 사실이 있을 때만 끌어온다.
5. scale 관련 표현은 원문에 근거가 있을 때만 쓴다.
6. 애매하면 더 약한 표현으로 내린다.

## 7. 출력 객체 권장안

fact-check 단계는 최소 아래 객체를 남길 수 있어야 한다.

```json
{
  "gate_a_result": "pass",
  "checks": [
    {
      "check_type": "new_metric",
      "status": "pass",
      "evidence_refs": ["exp_1.ach_2"],
      "note": "30% improvement exists in source"
    },
    {
      "check_type": "role_inflation",
      "status": "fail",
      "evidence_refs": [],
      "note": "lead/owner expression unsupported by source"
    }
  ],
  "required_actions": [
    "downgrade_claim",
    "remove_sentence"
  ]
}
```

## 8. 실패 시 처리

`Gate A = fail`이면 아래 중 하나로만 진행한다.

- 문장 제거
- 더 약한 표현으로 자동 재작성 후 재검사
- 사용자 확인 필요 상태로 남김

그대로 PDF 출력 단계로 넘기지 않는다.

## 9. 사용자 표시 정책

사용자에게는 내부 검사 규칙 전체를 그대로 노출하지 않아도 된다.

대신 아래 수준은 보여주는 것이 좋다.

- `이 문장은 원문 근거가 약해 보수적으로 수정되었습니다`
- `이 문장은 원문에 없는 수치가 포함되어 제거되었습니다`
- `이 표현은 근거가 부족해 직접 확인이 필요합니다`

즉, 내부 정책은 엄격하게 두고, 사용자 메시지는 간단하게 유지한다.

## 10. v0 Open Decisions

- 위험 패턴 탐지를 어느 정도까지 규칙 기반으로 처리할지
- `사용자 확인 필요` 상태를 v0에서 허용할지
- LLM 2차 검토를 항상 돌릴지, 규칙 실패 케이스에만 돌릴지
