# Backend Resume Rubric v0

- 상태: `draft`
- 마지막 수정일: `2026-04-10`
- 작성자: `lsh`

## 1. 목적

이 문서는 경력직 백엔드 개발자용 `맞춤 이력서 초안`의 품질을 안정적으로 평가하기 위한 최소 내부 기준이다.

이 rubric은 아래 용도로만 쓴다.

- 재작성 전 약점 파악
- 재작성 후 결과 품질 점검
- 근거와 수정 이유 생성
- 프롬프트/모델 변경 후 품질 회귀 확인

이 rubric은 아래 용도로는 쓰지 않는다.

- 합격 확률 예측
- 사용자에게 절대적인 채용 점수 제공
- recruiter의 실제 판단을 완전히 대체

## 2. 적용 범위

대상:

- 경력직 백엔드 개발자
- JD 1개에 맞춰 재작성된 이력서 초안

전제:

- 사용자가 추출 텍스트를 한 번 확인하거나 수정했다.
- JD는 [JD Schema v1](../schemas/jd-schema-v1.md) 형태로 구조화됐다.
- 이력서는 [Resume Schema v1](../schemas/resume-schema-v1.md) 형태로 구조화됐다.

## 3. 평가 구조

평가는 `게이트`와 `점수 항목`으로 나눈다.

- 게이트: 어기면 총점이 높아도 실패다.
- 점수 항목: 통과한 결과 안에서 상대적인 품질을 본다.

## 4. 게이트 조건

### Gate A. 사실 보존

실패 조건:

- 원문에 없는 경험이 추가됨
- 원문에 없는 수치가 추가됨
- 실제보다 큰 역할이나 책임이 단정적으로 부풀려짐

판정:

- `pass`
- `fail`

메모:

- v0에서 가장 중요한 불변식이다.

### Gate B. 근거 추적 가능성

실패 조건:

- 재작성된 핵심 문장이 원문 어느 부분을 근거로 했는지 추적할 수 없음
- JD 반영 포인트가 어떤 requirement에 대응하는지 설명할 수 없음

판정:

- `pass`
- `fail`

### Gate C. 사용자 검토 가능성

실패 조건:

- 변경 diff가 제공되지 않음
- 사용자가 수정하거나 되돌릴 수 없는 상태로만 결과가 제공됨

판정:

- `pass`
- `fail`

## 5. 점수 항목

총점은 100점 만점이며, 게이트를 모두 통과했을 때만 계산한다.

| 항목 | 가중치 | 질문 |
| --- | --- | --- |
| JD 핵심요건 반영도 | 30 | JD의 필수 요구사항과 핵심 업무가 이력서에 제대로 반영됐는가 |
| 백엔드 적합성 드러남 | 25 | 백엔드 경력자에게 중요한 경험이 충분히 드러나는가 |
| 성과와 임팩트 명확성 | 20 | 성과가 구체적이고 가능하면 정량적으로 드러나는가 |
| 문장 명확성과 스캔 용이성 | 15 | 짧고 명확하게 읽히며 빠르게 훑어볼 수 있는가 |
| 구조 일관성과 강조 우선순위 | 10 | 중요한 경험이 앞에 오고, 구조가 JD 목적에 맞게 정렬됐는가 |

## 6. 점수 기준

각 항목은 0점부터 3점까지 준다.

- `0`: 거의 반영되지 않음
- `1`: 일부 반영됐지만 부족함
- `2`: 대체로 적절함
- `3`: 매우 적절함

최종 점수는 아래 방식으로 계산한다.

`(항목 점수 / 3) * 가중치`

## 7. 항목별 세부 기준

### 7.1 JD 핵심요건 반영도

무엇을 보나:

- 필수 기술 요구사항 대응
- 주요 업무와 관련된 경험 강조
- 연차/숙련도에 맞는 경험 배치

점수 기준:

- `0`: JD 핵심 요구사항 대부분이 반영되지 않음
- `1`: 일부 키워드만 반영되고 실제 업무 대응이 약함
- `2`: 핵심 requirement 다수가 반영되고 대응 근거가 보임
- `3`: 필수 requirement와 주요 업무가 명확하게 대응되며 우선순위도 적절함

### 7.2 백엔드 적합성 드러남

무엇을 보나:

- 시스템 설계/구현 경험
- 데이터베이스/트랜잭션 이해
- 성능/확장성/안정성 경험
- 운영/관측 가능성, 배포/장애 대응 경험

점수 기준:

- `0`: 백엔드 핵심 경험이 거의 드러나지 않음
- `1`: 기술 키워드는 있으나 깊이나 맥락이 약함
- `2`: 백엔드 경력자로서 의미 있는 경험이 적절히 드러남
- `3`: JD와 연결되는 백엔드 경험이 구체적으로 강하게 드러남

### 7.3 성과와 임팩트 명확성

무엇을 보나:

- 결과 중심 표현 여부
- 수치/규모/변화량 제시 여부
- 단순 업무 나열이 아닌 문제-행동-결과 구조 존재 여부

점수 기준:

- `0`: 업무 나열 위주이며 결과나 임팩트가 거의 없음
- `1`: 일부 결과가 있으나 추상적이거나 약함
- `2`: 다수 항목에서 결과와 임팩트가 드러남
- `3`: 핵심 경험이 결과 중심으로 정리되고, 정량 표현도 충분함

### 7.4 문장 명확성과 스캔 용이성

무엇을 보나:

- 불필요하게 긴 문장 여부
- 중복 표현 여부
- 빠르게 훑어도 요지가 보이는지

점수 기준:

- `0`: 장황하거나 모호해서 빠른 스캔이 어려움
- `1`: 읽을 수는 있으나 불필요한 문장과 중복이 많음
- `2`: 대체로 명확하고 읽기 쉬움
- `3`: 매우 간결하고 명확하며 핵심만 빠르게 파악 가능함

### 7.5 구조 일관성과 강조 우선순위

무엇을 보나:

- 중요한 경험이 상단에 오는지
- JD와 관련 없는 항목이 과도하게 강조되지 않는지
- 요약, 경험, 프로젝트, 기술 스택의 흐름이 자연스러운지

점수 기준:

- `0`: 구조가 산만하고 강조 우선순위가 맞지 않음
- `1`: 기본 구조는 있으나 JD 목적과 정렬이 약함
- `2`: 구조가 대체로 안정적이고 강조 우선순위도 적절함
- `3`: JD 목적에 맞게 구조와 순서가 매우 잘 정렬됨

## 8. 출력 형식 권장안

평가 엔진은 최소 아래 객체를 만들 수 있어야 한다.

```json
{
  "gate_result": {
    "factual_fidelity": "pass",
    "evidence_traceability": "pass",
    "user_reviewability": "pass"
  },
  "scores": {
    "jd_coverage": 0,
    "backend_relevance": 0,
    "impact_clarity": 0,
    "clarity_and_scanability": 0,
    "structure_and_priority": 0
  },
  "weighted_total": 0,
  "evidence": [],
  "rewrite_priorities": []
}
```

## 9. 해석 기준

- `85~100`: 매우 강함. 사용자 최종 검토 후 바로 출력 가능한 수준
- `70~84`: 실용적임. 일부 수동 수정 후 사용 가능
- `50~69`: 약함. JD 반영 또는 임팩트 표현 보강 필요
- `0~49`: 부적합. 구조 재작성 또는 입력 품질 재점검 필요

단, 게이트 실패 시 총점과 무관하게 `출력 불가` 또는 `재작성 재시도`로 처리한다.

## 10. v0 Open Decisions

- `백엔드 적합성` 안에서 시스템 설계와 운영 경험 비중을 더 쪼갤지 여부
- 사실 오류 검출을 규칙 기반과 LLM 검토 중 어떻게 조합할지
- 사용자가 실제로 보게 되는 점수 UI를 둘지, 내부 품질 통제용으로만 유지할지
